# PKEY2009 format

25 characters from a 24-symbol alphabet (no vowels, no `0/1/5`), in five
groups of five:

```
alphabet: BCDFGHJKMPQRTVWXY2346789
example:  NVTDK-QB8J9-M28GR-92BPC-BTHXK
```

One slot is the literal `N`; its position encodes a data digit. The leading
digit gives that position, and the 25 base-24 digits decode to a 114-bit
integer:

| bits | field | width | meaning |
|---|---|---|---|
| 0–19 | group | 20 | SKU id (e.g. 5219 = SQL 2025 Enterprise) |
| 20–49 | serial | 30 | per-SKU serial |
| 50–102 | security | 53 | opaque; any value passes |
| 103–112 | checksum | 10 | CRC-32 of the other fields |
| 113 | upgrade | 1 | upgrade/variant flag |

**Checksum:** zero bits 103–112, build the 16-byte little-endian block, then
`(~CRC32(block)) & 0x3FF` with poly `0x04C11DB7`, init `0xFFFFFFFF`, standard
final inversion. CRC-32 is GF(2)-linear, so `ck = CONST XOR masks[k]` over set
bits `k` — the table in `res/crc_full_masks.json`.

It is **not** an HMAC: `pidgenx.dll` imports no HMAC/SHA-256 and accepts any
`security` value; exactly one of 1024 checksums returns `HRESULT=0`.

Encoder/decoder: `encode()` / `decode()` in `pkey2009/keygen.py`.

```python
>>> encode(5219, 0, 0x1F80524E0F41AA, 0x335, 1)
'B64XM-XC68Y-XRM4N-MTX7B-MY9J4'
>>> decode('B64XM-XC68Y-XRM4N-MTX7B-MY9J4')
{'group': 5219, 'serial': 0, 'security': 0x1F80524E0F41AA,
 'checksum': 0x335, 'upgrade': 1}
```
